# Native split lane prefill floor: analysis (1 Nov 2026)

Written by a read-only Opus analyst subagent and saved by the lead, because the harness blocked the subagent's own write. Scratch scripts are in `scratch/`. Labels: **[M]** measured from a log or counter, **[D]** derived by arithmetic from measured values, **[I]** inferred, not measured. `S5/` means `<hub-dir>/agents/flash-next/wt-claude-native43-held/patches/s5_engine/`; the deployed overlay in bundle 118e8681c0eb differs only in its import lines.

## Executive summary
- **The floor is a host round-trip chain.** One solo chunk is ~141 host round trips run strictly one after another: open, bind, 48 layer commands, ~7.4 commands per QSA layer, polls, PP handoff, finalize, release.
  - Only one command is in flight at a time, and each goes to all 4 ranks.
  - Each round trip costs ~5.1 ms. The engine step loop sets that pace: 2.3 ms steps × ~2.2 steps per command, with an empty stock `execute_model` sent to all workers every step.
  - That accounts for ~0.65 s of the 0.72 s. Only 16 of the 141 commands are waits forced by the GPU.
  - The two PP stages also take turns, and most of the GPU's compute hides under the chain.
- **Decisive evidence.** Every 4-layer group takes ~22 engine steps on both stages. PP1 groups still take 35% longer, because steps are slower while PP1 (and rank 2, the stock output rank) is busy: 2.69 vs 1.91 ms. The GPU work per group is the same on both stages, so the GPU is not setting the pace.
  - Under live decode the same chain costs about one decode step per command: 2.79 s / 141 ≈ 20 ms.
- **Lever 1: cut the command count (~2–3.5× solo, more under live decode).** Run a group or stage per command on the worker, with the dense plan granted up front and the QSA bucket/tail ordered on the stream instead of host-polled. This takes ~141 commands down to ~15–25. Large build, memory-neutral, high gate risk, bitwise-identical arithmetic.
- **Lever 2: two chunks in flight across PP stages (~1.6–1.8× now, 1.7–1.9× once GPU-bound).** Needs stage-local release, one command stream per stage, and admission of the next chunk at PP0 finalize.
  - Costs ≈0 extra device MiB per rank: each worker still holds one chunk, and the PP double buffers (`PP_SLOTS=2`) already exist.
  - It gains nothing if commands stay single-in-flight across both stages.
- **Lever 3: stop pacing native commands with empty stock steps, and stop shipping O(n) reports in every reply (1.2–1.7× solo, uncertain until receipts).** Engine control CPU alone is 162 ms per chunk. held-f's burst only covers the live case.
- **Realistic ceiling during live decode** (44/38 SMs, 1,024 rows, levers 1 and 2 done): ~3,000–4,000 tok/s, centre ~3,500.
  - This rests on ~240–300 ms per stage at 38 SMs beside decode.
  - 2,048-row chunks would add ~15–20% if the memory can be funded.
  - Fixing the protocol without pipelining the stages tops out near ~1,600–2,100 tok/s.
  - Today: ~1,410 tok/s solo, ~370 tok/s live below the cliff, 217 tok/s over the whole held-e W2 run.
- **TP4: stay on TP2×PP2.** Stage turn-taking is our driver's choice, not inherent to PP. TP4 would lose the custom all-reduce, double each GPU's host-KV reads and row cache, and leave the host-bound floor in place.

**Why the floor is host-bound [D]:**
- PP0 groups are 43.3 ms = 22.7 steps of 1.91 ms. PP1 groups are 58.0 ms = 21.6 steps of 2.69 ms.
- The GPU work per group is the same on both stages; the x8 copy adds only ~1.7 ms per group.
- 22 × (2.69 − 1.91) ≈ 17 ms, which matches the +14.7 ms gap between PP1 and PP0 groups.
- Regression [M]: period = 619 + 1.40 × (QSA attention + copy), R² 0.57. GPU variance leaks in through the pending waits, but the ~620 ms intercept is not GPU.
- Live check [D]: 2.79 s / 141 ≈ 19.8 ms per command, about one decode step.

**Why steps are slower in the PP1 phase [I]:** rank 2 (PP1 TP0) is both the stock output rank and the x8 card. Its reply to the empty stock RPC is delayed while it runs native commands. This is the head-of-line coupling in held-f `design.md` §0.

| # | Mechanism | Source | Essential? |

| 9 | Monotone global `state_epoch` | `S5/engine_driver.py:2050–2053, 1619 ff` | choice; would become per stage |

**What is essential:**
- Stage-local order of GDN state and QSA K/V writes: chunk n+1 on PP0 needs chunk n's PP0 layers and its STATE_FINALIZE s0.
- The PP consumer receipt before a slot is reused.
- An identical command sequence on both TP peers, because the NCCL collectives must match.

None of these needs PP1 of chunk n to finish before PP0 of chunk n+1 starts. Stock V1 keeps pp+1 batches in flight (`flash-next-crazydiamond/reference/vllm-src/config/vllm.py:589–599`).

**Smallest change for two chunks in flight:**
1. **Engine:** a cursor per stage and one command in flight per stage, with replies sorted by stage. TP checks (`:1412–1421`) stay per stage.
2. **Scheduler:** admit chunk n+1 at PP0 finalize of chunk n, with two parked records. Computed tokens and the prefix-cache commit still advance only at chunk n's global release.
3. **Worker:** release locally after its own stage's finalize. The existing PP receipt carries slot ownership.
4. **Epoch:** one `state_epoch` per stage.

**Memory:** ≈0 extra device MiB per rank [D].
- Each worker still runs one chunk.
- `PrefillPPChannel` already allocates 2 slots of `[max_tokens, 10240]` bf16, ~40 MiB per rank (`S5/lane_comm.py:33, 261 ff`).
- KV blocks come from the existing pool.
- The extra state is host-side.
- Verify this against the open/release memory receipts.

**Gain [D]:**
- Today: period ≈ max of the two stage chains, ~70 commands at ~2.7 ms steps ≈ 0.40–0.45 s → **1.6–1.8×**.
- With commands only interleaved and still one in flight overall: ≈1.0×.
- Once GPU-bound: 1.7–1.9×.

**Risk and side effects:**
- High lifecycle risk (drain/cancel of two chunks, checkpoint exactness) and high leak-gate risk.
- TP agreement risk unchanged.
- Numerics bitwise identical.
- PP0 GPUs then carry prefill all the time, so decode there sees contention twice as often.

## Q3. The ceiling

**How stock's per-chunk time was derived (all at 1,024 rows, same as native) [D]:**
- held-b W2: 1024 / 7,797 tok/s = 0.131 s.
- held-e: 0.143–0.150 s.
- Solo 200k (24 Oct): 24.2 s / 197k = 0.126 s.
- 12×32k: 0.115 s.
- One stage is ~118–125 ms busy (`fn-main/README.md:117`; `STALL-PLAN.md` 24 Oct 07:48 trace).
- So stock's period ≈ one stage time: stock pipelines the PP stages (`README.md:113`).

**Where the ≈5.5× gap comes from (factors multiply):**

| Factor | Size |
|---|---|
| Chunk size | 1.0× [M]. Stock itself gains 16–20% at 2,048 (10,296 vs 8,866 tok/s; 20.1 vs 24.2 s) |
| SM share, solo, 38 of 82 SMs | ×1.4–2.2 [D/I]. MPS at 50% gave 1.37× (`STALL-PLAN.md` 24 Oct 11:14); the pure SM ratio is 2.16 |
| No PP pipelining | ×2 [D] |
| Exposed host protocol | ×~1.7–2.2 [I] (724 ms vs ~330–420 ms of serialized GPU time) |

**Contention with decode:**
- The green split partitions SMs, not DRAM, PCIe or the copy engines.
- The dense copy and decode's host-KV gathers (decode's known limiter) share PCIe. Rank 2 on the x8 link is the worst case: copy 25.3 vs 14.9 ms [M].
- The synthetic green-split test at 38 SMs beside decode gave 50% of full-GPU prefill on the x16 pair and 41% on the x8 pair [M] (`STALL-PLAN.md` 24 Oct 16:11). It is optimistic: BF16 GEMMs, no prefill PCIe traffic.
- That puts live per-stage time at 118–125 / (0.41–0.50) ≈ **240–300 ms** [D]. Solo at 38 SMs ≈ 145–250 ms [I].

**Ceilings:**

| State | Solo | Live decode |
|---|---:|---:|
| Today | 1,410 [M] | ~370 below the cliff [M]; 217 over the whole W2 [M] |
| Protocol removed, stages still take turns | ~2,000–3,500 | **~1,700–2,100** |
| Protocol removed + PP pipelined | ~4,100–6,000 | **~3,400–4,300 overhead-free; ~3,000–4,000 realistic** |
| + 2,048 rows (unfunded today) | +15–25% | ~3,500–4,500 |

The operator's ~4,000 tok/s with decode ~0.9 sits only at the top of the pipelined range. It probably also needs 2,048 rows or full-SM solo phases (L6).

## TP2×PP2 vs TP4

**(a) Stage turn-taking is our driver's choice, not inherent to PP.**
- Stock V1 keeps pp+1 batches in flight (`vllm.py:589–599`).
- On this box stock's period ≈ one stage time (0.126–0.131 s vs ~118–125 ms per stage).
- Our serialization comes from mechanisms 1–5 and 9 in Q2. PP itself needs only stage-local order plus the PP receipt.

**(b) Cost of TP4:**
- **Custom all-reduce lost.** vLLM disables it above 2 GPUs unless all are NVLink-connected (`reference/vllm-src/distributed/device_communicators/custom_all_reduce.py:236–242`; NVML check at `platforms/cuda.py:835`). Here only the pairs are NV4 (`reviews/codex-20261025s-s5-engine-design.md:76–81`).
- **Twice the collectives, over PCIe.** All 96 all-reduces per forward per rank (vs 48 now) would go through NCCL across PCIe, including the x8 link.
- **Real decode cost.** Custom all-reduce was worth +27% decode (`README.md` table: 281.7 → 357.5).
- **Link contention.** Native prefill's ~5 MiB all-reduces [I] would share links with decode's small ones and with the host-KV gathers.
- **Divisibility.** Attention heads (24/4) and GDN heads (16/4, 48/4) divide; experts go to EP4 with 128 local. **KV heads 2 < 4 → replicated.** The QSA helper supports replication (`results/vm<vm-id>/job14/helpers/qsa_native.py:443–449`), but its decode configs are tuned for TP2 (`results/vm<vm-id>/job14b/helpers/ops_qsa_native.py:526, 541`).
- **Memory.** Weights stay ~18 GiB per rank. But each rank would hold 12 QSA layers instead of 6:
  - per-GPU host-KV reads per decode token double;
  - the row cache goes from 0.64 to ~1.3 GiB per rank, which doesn't fit (`docs/MEMORY-LEDGER.md`);
  - replicated host KV doubles pinned host memory (4 × ~31 → ~62 GiB, over the 240 GiB CT limit) unless the replicas share one buffer.
- **Code.** E3 assumes two stages (`reviews/codex-20261029-native18-box-premortem.md:7`), so startup, plan, TP agreement and every gate would need requalifying.

**(c) Gain from TP4:**
- One stage across all 4 prefill partitions, with no handoff or bubbles. That is what L2 gives.
- No PP2 decode ring (`README.md:113`).
- A simpler driver.
- The host-bound floor stays put (~135 commands per chunk), so TP4 prefill is no faster until L1 lands.

**(d) When TP4 would win, and the cheapest test:**
- TP4 wins only if both hold:
  - L2 proves infeasible under the lifecycle, cancel and leak gates;
  - stock TP4 keeps W1 decode ≥ ~0.95× of TP2×PP2, with the row cache and replicated KV fitting.
- Expectation: TP4 decode loses clearly [I].
- Cheapest settle: a stock-only A/B with `harness/run_flash_tuning.sh` at `TP=4 PP=1`.
  - Those are the script's own defaults at `:59`; `harness/flash-tuning.env` overrides them to 2/2.
  - Run W1 8-stream decode plus a solo fresh-prompt TTFT at chunk 1,024, at a context reduced enough to fit replicated KV.
  - ~1.5–2 h of box time. Run it only if L2 stalls.
- **Prior record:** no Flash-Next TP4 measurement exists.
  - TP2×PP2 has been the topology since the 21 Oct reference (`README.md:6`). Both premortems state it as a constraint (`reviews/codex-20261029-native18-box-premortem.md:7`, `reviews/owner-20261029-native18-box-premortem-independent.md:16`).
  - The "tp4" in `/data/vllm/flash-next-tp4` and in the served model name `qwen38-w8a8-tp4` is left over from the 27B W8A8 TP=4 production (`harness/run-awq-bf16.sh:34`).
  - Records that say "TP4 engine" (e.g. `results/box/q18a-native28-run-1/README.md:32`) are loose wording; that engine is TP2×PP2.
